# 本地模型对比实验：上下文核查验证集（2026-11-12）

**性质**：对比实验，只看结果。**不根据结果改任何流水线代码**；流水线、提示词、判定代码、DeepSeek 的缓存 / 账本 / 验收结果都未改动。
实验脚本：`scripts/compare_local_models.py`（运行）、`scripts/analyze_local_comparison.py`（出表）。原始结果在 `out_alt/<模型标签>/`（不进仓库），完整表格见 `out_alt/comparison_tables.md`。

## 1. 设置

| | DeepSeek（基准） | Qwen3.5-9B | MedGemma 1.5 4B |
| --- | --- | --- | --- |

| 量化 | — | MLX 4bit（affine，group size 64），加载后 5.57 GiB | MLX 4bit（group size 64），加载后 3.20 GiB |
| 思考 | reasoning_effort **low** | **不思考**（见下） | 无思考模式 |
| JSON | `response_format: json_object` | **JSON Schema**（同一回答结构） | **JSON Schema** |
| 温度 | 0 | 0 和 0.7 各跑一次 | 0 和 0.7 各跑一次 |
| 结果来源 | 已有的复核结果 `out/context_check_validation.json`（v3，未重跑） | 本次 | 本次 |

相同的：26 条（13 条写错 + 13 条正确），每条 3 次调用共 81 次；提示词 `context-check-v3` 逐字相同；判定代码（`decide_3a` / `decide_3c`）和误伤口径（状态被改变或先例被剔除）相同。

**与 DeepSeek 的两处设置差异**（用户 2026-11-12 同意）：
1. **JSON 方式**：LM Studio 不接受 `json_object`（返回 400："'response_format.type' must be 'json_schema' or 'text'"），改为 JSON Schema 约束同一结构 `{"answers":[{q, answer, quote}]}`。
2. **思考**：Qwen3.5 开思考时 8 000 词元仍未想完（约 18 词元/秒，一次调用数分钟，81 次不可行）；`reasoning_effort: low / none`、`chat_template_kwargs.enable_thinking: false` 三种参数 LM Studio 都忽略（输出逐字相同）。在 JSON Schema 约束下模型不思考、直接写 JSON，但 LM Studio 把它放进 `reasoning_content`、`content` 为空——实验脚本在 `content` 为空且 `reasoning_content` 是合法 JSON 时采用后者（81/81 次都走了这条）。**所以 Qwen 是"不思考"对 DeepSeek 的"低档思考"**，对 Qwen 偏不利。

**隔离**：本地运行的进程删除了 DeepSeek key、接口固定为 127.0.0.1 且每次调用前复核；缓存 / 调用记录 / 结果都在 `out_alt/`；本地故障只会报错退出（冒烟测试的 400 和空回答都是这样停下的），从未调用收费 API。

## 4. 逐题

只列有模型判错的题，其余 21 题五列全部判对（完整 26 行见 `out_alt/comparison_tables.md`）。

| 病例 | 条目 | 类别 | DeepSeek | Qwen t0 | Qwen t0.7 | MedGemma t0 | MedGemma t0.7 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| BLIND-RRM2B | valproic acid | 3a 状态（例外从句极性） | ✓ | ✓ | ✗ 仍为有条件 | ✗ 仍为有条件 | ✗ 仍为有条件 |
| BLIND-GEMIN5 | Coenzyme Q10 | 疗效方向 | ✓ | ✓ | ✗ 方向未报告 → 证据不足 | ✓ | ✓ |
| BLIND-MPZ | voriconazole | 不良反应当先例 | ✓ | ✓ | ✓ | ✗ 当成治疗先例 | ✓ |
| BLIND-RRM2B | catabolism | 正确 3a | ✓ | ✗ 有条件 → 适用 | ✗ 有条件 → 适用 | ✓ | ✓ |
| AITX-00007 | dopamine receptor antagonists | 正确 3a | ✓ | ✓ | ✓ | ✗ 适用 → 有条件 | ✓ |

错因：
- **valproic acid**（三个本地运行都错）：原文 "should be used only in exceptional circumstances" 是"避免"的例外；MedGemma 把它同时当成"限定"和"例外"，状态不变。属阅读规则里的"禁忌语境下例外从句极性"，是这批里最难的一类。
- **catabolism**（Qwen 两次都错）：Qwen 把条件行"麻醉时间较长时"判成"避免的例外"，状态从"有条件"变"适用"——同一类极性错误，方向相反。
- **voriconazole**（MedGemma t0）：把"可能抑制多种药物清除"判为有害，但仍判用药目的为治疗（它在文中是抗真菌用药），先例未被剔除。
- **dopamine receptor antagonists**（MedGemma t0）：把药名列表本身当成"限定"，加了限定行。

MedGemma 在正确条目上加提示（不改状态）7 条，多于 DeepSeek 的 3 条：骨科手术、髋关节手术、亚叶酸钙、磷酸吡哆醛等，大多是把建议原句本身当成"限定"——不改状态，但给 Step 4 增加噪声。

## 7. 两种混用方式（只给判断，不实现）

**级联**（本地先判，3 票有分歧的条目交给 DeepSeek；按条目计）：

| 本地 | 交给 DeepSeek | 合并后判对 | 本地 3 票一致却判错（漏到最终结果） |
| --- | --- | --- | --- |
| Qwen t0 | 0/26 | 25/26 | catabolism（误伤） |
| Qwen t0.7 | 19/26（省 27 % 的 DeepSeek 调用） | 26/26 | 无 |
| MedGemma t0 | 1/26 | 23/26 | valproic、voriconazole、dopamine |
| MedGemma t0.7 | 11/26（省 58 %） | 25/26 | valproic（漏抓一条写错） |

判断：**不值得**。省得多的（MedGemma t0.7）会漏掉一条写错；不漏的（Qwen t0.7）只省约四分之一，而本地还要多跑 81 次。核查器全量一次约 \$0.7（练习病例），省下的钱不抵"写错比不写更糟"的风险；温度 0 下本地 3 票几乎从不分歧，级联退化为"全信本地"。

**交叉核查**（抓住或误伤这类改动，要两个模型都同意才生效）：

| 组合 | 判对 |
| --- | --- |
| DeepSeek & Qwen t0 | 26/26 |
| DeepSeek & MedGemma t0.7 | 25/26 |
| Qwen t0 & MedGemma t0.7 | 25/26 |
| Qwen t0 & MedGemma t0 | 24/26 |

判断：**暂不值得**。它能挡住单个模型的误伤（Qwen 的 catabolism），但同样会挡住只有一个模型抓到的写错（"都同意"对抓住和误伤一视同仁）。这套题上 DeepSeek 单独已是 13/13、0/13，加 Qwen 没有可测的收益；两个本地模型错的题基本不重合，看起来互补，但只有 26 题、每个模型 1–3 个错，样本太小，不足以下结论。

## 8. 一句话结论

**Qwen3.5-9B（MLX 4bit，不思考）在温度 0 时与 DeepSeek 最接近（抓住 13/13，误伤 1/13），MedGemma 1.5 4B 最快（每次 5.6–7.6 秒，约为 Qwen 的 2.6 倍快）但温度 0 时错 3 条；两者都不能替代 DeepSeek，级联和交叉核查在这套题上都不值得采用。**

**局限**：
- 26 条，一条 = 7.7 %；本地每个设置只跑了一次。
- **DeepSeek 一列是样本内成绩**：v3 的核查问题正是在这 26 条上改出来的（复核记录见 CLAUDE.md 例外记录），所以 DeepSeek 的 13/13、0/13 偏乐观；本地模型用的是同一套"为 DeepSeek 调过"的问题。真实表现以 4 例复测为准。
- Qwen 是不思考、DeepSeek 是低档思考；JSON 方式也不同（见第 1 节）。

## 9. 附：流水线里 DeepSeek 的温度与投票重合（只读缓存，未改代码）

| --- | --- | --- | --- |
| 上下文核查 · 3a 条目 | 308 | 80.5 % | 92.8 % |

**结论**：温度设为 0，但 DeepSeek 思考模式下 3 票**并不总相同**——上下文核查约 20 % 的调用至少有一个问题分歧，支持度核查约 35 %。后两次投票**不是浪费**：分歧时代码不做改动（要求一致），这是对单次读错的刹车；验证集上 DeepSeek 有 4 条分歧，4 条最终都判对。

两个方案的利弊（只报告，不改代码）：
- **只问 1 次**：调用和费用降到三分之一（全量重跑核查器约省 \$0.45）。代价是失去"分歧不改"的刹车，单次误读会直接改状态；需要先用验证集量"单票判错率"再决定。
- **提高温度让投票独立**：DeepSeek 思考模式下温度可能不起作用（官方对思考模式的采样参数支持需核实）；本地实验显示温度升高后分歧大增，抓住率下降（Qwen 13 → 11），误伤也下降（MedGemma 1 → 0）——它把核查器推向"更保守"。若要做，应在验证集上比较，而不是直接上线。
