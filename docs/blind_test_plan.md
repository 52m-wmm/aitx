# 盲测方案（草案 v0.1，2026-11-08；只写方案，未执行）

> 目的：在**没有被调过参的病例**上量出三个数——写错率、漏写率、有条件率——用来判断现在的流水线能不能交卷，以及哪些规则是对着已知用例调出来的（见 `docs/step3c_contract_todo.md` 的盲测重点检查项）。
> 前提：盲测期间**不改代码**。跑完先出数，再决定改什么；改完要重新抽一批新病例，不能在同一批上反复调。

## 1. 病例从哪来

手上能用的三类，各有短板：

| 来源 | 有多少 | 有没有标准答案 | 短板 |
| --- | --- | --- | --- |
| **A. Phase 1 Validator 数据集**（`data/cases/validation/phase1_hf_unseen_genes.json`） | **只有 2 个**（AITX-00007 / DDC，AITX-00011 / KCNT1） | **有**，但是单点问答式（例：\"英国批准该基因病的基因治疗最低年龄？\"，答案 \"18 months\"，来源 GeneReviews） | 数量太少；考的是单个事实，不是整份报告；而且这两个基因我们**已经起草过规则**（`data/rules/DDC.json`、`KCNT1.json`），严格说算不上完全未见 |
| **B. 未用过的 GeneReviews 基因** | GeneReviews 有数百个章节，本地已归档；练习病例只用了 10 个基因（AGXT、ANO10、CFTR、COL1A1、DMD、GRIN2B、KMT2B、NF1、OTC、SLC35A2），规则起草覆盖 16 个 | **没有**，要人工核对原文才能判对错 | 要先构造病人（变异 + 临床描述），构造方式本身会引入偏差 |
| **C. 4 个评测病例** | 4 | 没有 | **盲测不能用**（2026-11-08 决定已写进 CLAUDE.md，代码也加了 `--eval` 保险） |

### 定稿：A + B，共 12 个病例（2026-11-08 审阅）

- **A 组（2 个）**：Phase 1 Validator 的 DDC、KCNT1 两个病例全用，各自只核对它带标准答案的那一个事实，作为"有外部答案"的锚点。
- **B 组（10 个）**：**一半有 GeneReviews 专章，一半没有**（审阅决定），这样能分别量出"有现成章节"和"只能靠数据库"两种情形下的表现：

| 子组 | 抽 | 从哪抽 | 临床描述 |
| --- | --- | --- | --- |
| **B1 有专章** | 5 个基因 | 本地 GeneReviews 归档里有 OMIM 疾病号、且不在已用 16 个基因里的章节 | 逐字取该章节 Clinical Characteristics 第一段列出的 2–4 条表型 |
| **B2 无专章** | 5 个基因 | **GenCC 评级为 Definitive**、且在 GeneReviews 里没有专章、也不在已用基因里 | **由代码按该病的 HPO 表型生成**（2026-11-08 定）：只取频率为 Obligate / Very frequent / Frequent 的表型，按频率从高到低；不足 2 条时按频率往下补到 2 条，最多 4 条；每条记录取它的理由（频率带 + 原始值）。病例 JSON 标 `"description_source": "synthetic_from_hpo"`，报告里也要能看出这一点 |

**抽样规则（写死、可复现，脚本 `scripts/sample_blind_cases.py`，无 LLM）**：
1. 候选池：两池都要求 GenCC 评级 Definitive、且该病能映射到 OMIM 号（B2 的描述要用按 OMIM 建索引的 HPO 注释，映射不到就没法生成）；B1 要求该基因有 GeneReviews 专章，B2 要求没有。剔除名单见下。
   **数据快照必须钉死**：抽样只读 `.cache/datasets/<数据集>/<日期>/` 里已有的快照，**不触发任何下载**，快照日期写进 `sample.json`。起因：2026-11-08 两次运行之间 `ensure_all()` 刷新了数据集，B2 候选池从 1020 变成 1021，抽中的基因就变了两个——盲测的抽样必须可复现。
2. 排序：按基因符号字典序排好，消除来源顺序的影响。
3. 抽样：`random.Random("blind-2026-11-08").sample(pool, 5)`，种子写进脚本常量，抽样结果连同两个候选池的大小一起写入 `out/blind/<批次>/sample.json`。
4. 变异：取 ClinVar 中该基因**评级为 Pathogenic**、标题里给出转录本和 c. 变化、且**位于编码区**的变异里，**VCV 登记号最小**的那一条。"提交最早"操作化成"登记号最小"：ClinVar 的登记号是按顺序发的，而且任何人都能从记录上读到，不像提交日期因提交者而异。**内含子变异不取**（标题里 c. 位置带 +/- 的），因为 Step 1 要读蛋白层后果——CTDP1 就因此被跳过（它在 ClinVar 里唯一的非 CNV 致病变异是内含子奠基者变异 c.863+389C>T）。
5. 合子状态：由 GenCC 记录的遗传方式决定（X 连锁 → 半合子，常染色体隐性 → 纯合，其余 → 杂合），不由我判断。
6. 跳过与替补：某个基因取不到合格变异就跳过，按同一个种子排出的顺序取下一个，**每次跳过都记进 `sample.json`**。
7. **抽到哪些基因先给你看**，你确认后才跑 Step 1–3。

**剔除名单（写死在 `scripts/sample_blind_cases.py`）**：
- **评测病例的基因 ACTL6B、ITPR1、SPTLC1、SYT1：永久剔除**，不进任何盲测或调参用的病例集（2026-11-08 决定）。
- 练习病例的 10 个基因（AGXT、ANO10、CFTR、COL1A1、DMD、GRIN2B、KMT2B、NF1、OTC、SLC35A2）：流水线是在它们身上调出来的。
- Phase 1 Validator 的 DDC、KCNT1：作为 A 组单独使用。

**合成描述的风险要写在报告里**：B2 的描述不是真实病历，HPO 频率最高的表型未必在同一个病人身上共存。所以 B2 的统计单独列一栏，不与 B1、A 混在一起算总率。

## 2. 怎么统计

每份报告按**条目**（account 里的一条 action / 一条 modality 判定 / 一条候选）逐条判，判完汇总。判定由你（或你指定的人）做，我只提供表格和原文链接，不参与判对错。

| 类别 | 定义（可判定，不含"感觉不好"） | 怎么数 |
| --- | --- | --- |
| **写错（wrong）** | 满足任一条：① 该条目的结论与它引用的原文矛盾；② 引用的记录里根本没有这句话（引文不可解析或非逐字）；③ 方向错（如对功能丧失病人给拮抗剂）；④ 放错章节（有人体先例的放进 3e、定制手段放进 3e 等）；⑤ 适用性判错（原文明确否认的条件判成满足） | 每条算 1；一条同时犯多项仍算 1，但记下所有命中项 |
| **漏写（missed）** | 该基因的来源里**明确写了**、且属于本报告某一章节的治疗性条目，报告里任何章节都没出现。判定范围限定在三类来源：GeneReviews 该章节的 Management 节、FDA 说明书里以该病为适应症的药、ClinicalTrials.gov 上招募中且 Conditions 命名该病的试验 | 每个遗漏条目算 1；**只在上述三类来源里找**，不要求穷尽文献 |
| **有条件（conditional）** | 条目本身成立、方向和章节都对，但因病人事实缺失而判为 conditional / unable_to_assess | 每条算 1，并记下缺的是哪个变量 |
| **无法评估（unassessable）** | 3d / 3e 特有：因暂缓接入的数据源（结构域、PAM、基因剂量）判不了 | 单独统计，不计入写错 |

**三个核心数**（每个病例算一次，再取总体）：
- 写错率 = 写错条数 / 报告写出的总条数 —— **这是最重要的一个**，评分标准是"写错比不写更糟"
- 漏写率 = 漏写条数 / （报告写出的正确条数 + 漏写条数）
- 有条件率 = 有条件条数 / 报告写出的总条数

**附带要盯的项**（来自已记录的盲测重点检查项）：
1. 3c 的检索排序：背景词频率阈值 0.15、酶名排除、按药轮流取、主要设计召回路径；
2. 3c 的基因家族名规则（前缀 ≥ 4 字母）——重点看**同家族不同成员**会不会串（CACNA1A / CACNA1C 这类）；
3. 3e 的排序权重与两个上限（10 条 / 无实验证据最多 3 条）；
4. L4 对症指南的覆盖率（有多少症状落不到任何类别）。

### 判定分工（2026-11-08 定）

**机器先判（代码，无 LLM，不涉及医学判断）**：
1. 引文是否逐字出现在它引用的来源文本里（沿用账本已有的 `quote_in`）；
2. 记录 id 是否可解析（PMID / NCT / setid / CHEMBL / R-HSA / NBK 能否取回该记录）；
3. 章节归属是否违反硬规则（同一行动跨章节、有人体先例却留在 3e、定制手段出现在 3e）；
4. 方向是否与 3d 给出的机制相符（3e）；
5. 结论措辞是否出现禁用词或剂量；
6. 适用性判定是否与账本里记录的病人事实一致（条件说"满足"但事实是 unknown 之类）。
   这六项任何一项不过，直接计入**写错**，并在判定表里标明是机器判的、违反了哪一条。

**留给你判（需要医学判断）**，逐条列出、附原文链接和片段：
1. 结论与原文的**语义**是否一致（引文逐字但意思被扭曲）；
2. 该条目是否真的适用于这个病人（年龄、表型、合子状态的临床含义）；
3. **漏写**：在 GeneReviews Management 节、FDA 说明书、招募中试验这三类来源里，有没有该写而没写的；
4. 优先级与校准是否离谱（这条只记印象，不计入三个率）。

**判定表**：`out/blind/<批次>/review.html`，每条一行：章节、结论句、引用链接、原文片段、机器判定结果（通过 / 违反第 N 条）、右侧四个单选（对 / 写错 / 有条件 / 存疑）和"漏写"填写区。判定结果存 JSON，统计脚本只读这个 JSON。预计需要你判的条数约为总条数的三到四成（其余由机器判掉）。

## 4. 执行顺序

1. 抽样脚本 + 病例构造（确定性，无 LLM）→ **先把抽到的基因、变异和描述给你看**，同时记下当时的代码指纹和 git 提交号；
2. 你确认后冻结代码，跑 Step 1–3（非高峰、守当天预算上限）；
3. 机器判定（六项可机判的检查）→ 生成判定表，列出需要你判的条目；
4. 你判定 → 统计脚本出三个率 + 盲测重点检查项的结论（B1 / B2 / A 三栏分开）；
5. 写 `docs/blind_test_results.md`；**然后**才按第 6 节的顺序决定改什么。

## 5. 代码冻结（2026-11-08 定）

盲测期间**冻结代码**：从抽样确认那一刻起，`aitx/`、`config/`、`scripts/run_pipeline.py` 不得改动（这正是 `runmeta.code_fingerprint` 覆盖的范围）。
- 抽样确认时记下当时的代码指纹和 git 提交号，写进 `out/blind/<批次>/sample.json`；
- 跑完后再核一次指纹，不一致则这批数据作废重跑；
- 冻结期内发现 bug 也**不改**，记进 `out/blind/<批次>/found_during_freeze.md`，等这批跑完、数出来之后一起修。
理由：中途改了代码，前后病例就不是同一个系统产出的，三个率没法合并统计。

## 6. 写错率偏高怎么办（2026-11-08 定）

**处理顺序是固定的，不临场决定**：

1. **先做通用修复**，不针对单个病例打补丁：修完要能说清"这类错误"是什么、规则改在哪一层、反向测试是什么。沿用现有的审批规则（会产生新"不适用"的改动先报批）。
2. **修完换一小批新病例验证**（按同样的抽样规则、换种子抽 4–6 个），**不在同一批上重跑**——在同一批上反复修就是在对盲测集过拟合，和对评测病例过拟合是同一个毛病。
3. **按章节定门槛**：
   - **3a（已确立层）出现写错**：必须修好，或把该条改判为"有条件"，**才能进 Step 4**。已确立层是评审最容易核对的一层，这里写错最伤"事实准确性"。
   - **3b / 3c**：写错必须修好或降级为条件语句；无法在冻结后的新一批上复现的，记为待观察。
   - **3d / 3e（假设性层）出现写错**：**降级措辞或整节写"无法评估"**。这两节本来就是假设，把话说轻、或者整节承认"现有数据不足以判断"，都比写错强。
4. 每一轮的三个率、改了什么、下一批的结果，都记进 `docs/blind_test_results.md`，一轮一节，不覆盖。
